# hydrothermal-vents — build notes

Collection: `s3://public-high-seas/hydrothermal-vents/`
Source: InterRidge Global Database of Active Submarine Hydrothermal Vent Fields v3.4
(Beaulieu & Szafrański 2020, PANGAEA doi:10.1594/PANGAEA.917894), `CC-BY-NC-SA-4.0`.

721 point features (666 confirmed/inferred active, 55 inactive), global, all ocean basins.

## Resolutions

| | value |
|---|---|
| `h3:native_resolution` | **10** — point data; each vent field resolves to one ~15,000 m² cell |
| `h3:parent_resolutions` | **9, 8, 0** |

Resolution 8 is the catalog's universal join key and 0 is the hive partition key, so both
are mandatory for anything hexed finer than 8. The original April 2026 build carried only
`h10` + `h0`; resolution 9 and 8 were added by the #574 re-hex.

## ⛔ The convert step reads the published parquet as its own source

`hydrothermal-vents-convert.yaml` has, and has always had:

```
cng-convert-to-parquet \
  https://s3-west.nrp-nautilus.io/public-high-seas/hydrothermal-vents.parquet \
  s3://public-high-seas/hydrothermal-vents.parquet
```

Input and output are **the same object**. Running it rewrites the published flat in place,
and because `cng-datasets` synthesizes `_cng_fid` fresh at conversion time, the rewrite
**renumbers every feature id**. Nothing downstream is regenerated by that job, so the hex
and the flat silently stop agreeing on what `_cng_fid` 42 means.

That is a latent hazard in this recipe, and it is why the orchestrator must not be run here.

**It is not, however, what caused #574** — an earlier revision of this file said it was, and
that was wrong. The 2026-07-09 rewrite came from the **#372 `_cng_fid` backfill**,
`catalog/backfill/k8s/cngfid-372/catA-cngfid-convert.yaml`, which ran `cng-convert-to-parquet`
over ten datasets in a single pass and promoted each staged result. `hydrothermal-vents`
(13:07) and `iucn/iucn-ranges-2025` (13:10) are both on its list, which is why two unrelated
collections lost their hex↔flat key on the same afternoon (#574, #577).

The effect was the same either way: the hex was built 2026-04-22 (ids 0…720), the flat was
renumbered 2026-07-09 (ids 1…721), and for 78 days a consumer joining hex→flat on the
documented universal key got **the wrong vent field on all 720 overlapping rows** — with no
row-count or coverage symptom to notice. It was caught only when `check_hex_fid_matches_flat`
(#549) first ran against the pre-gate cohort.

**The general lesson is not about this recipe.** Any job that re-runs `cng-convert-to-parquet`
over a published flat renumbers `_cng_fid` and orphans every hex built from it, whether that
job lives in this directory or in a catalog-wide backfill. A flat that is re-converted needs
its hex (and anything else keyed to it) rebuilt in the same pass.

**Why this one was cheap to fix.** The damage here was a uniform **+1 shift** — the tool's id
base moved from 0 to 1 and the row order did not change — so the hex could have been re-keyed
losslessly, and a full re-hex of 721 points was minutes anyway. Compare `iucn/iucn-ranges-2025`
(#577), hit by the *same* backfill on the same afternoon but costing a 4-billion-row rewrite:
its flat had been **reordered** by a `sci_name` sort in between, so the re-convert assigned ids
in a new order and produced an unrelated permutation rather than an offset.

The transferable rule: **re-convert alone is recoverable in place; reorder-then-re-convert is
not.** A sort/cluster job is harmless by itself (it preserves ids) and unsafe in combination —
it removes the cheap escape from a renumbering that has not happened yet. If a published flat
is ever reordered, treat every hex built from it as stale from that moment.

**So:**

- **Do not run `workflow.yaml` (the orchestrator) on this dataset.** Its DAG starts with
  setup-bucket → convert, so it re-triggers the renumbering before it re-hexes.
- **Re-hex by applying the two job manifests directly**, which read the flat and never write it:
  ```bash
  kubectl apply -n geo-workflows -f hydrothermal-vents-hex.yaml
  kubectl wait  -n geo-workflows job/hydrothermal-vents-hex --for=condition=complete --timeout=1800s
  kubectl apply -n geo-workflows -f hydrothermal-vents-repartition.yaml
  kubectl wait  -n geo-workflows job/hydrothermal-vents-repartition --for=condition=complete --timeout=1800s
  ```
- **If the flat ever is re-converted, the hex and the PMTiles are both stale by definition**
  and must be rebuilt from it in the same pass.

The upstream source is a PANGAEA download, not this S3 object; a genuine re-ingest should
point `--source-url` at PANGAEA rather than at our own output.

## Re-hexing: the h0 partition set is stable, so overwrite is sufficient

`repartition` writes with `OVERWRITE_OR_IGNORE`, which only replaces the `h0=` partitions the
new build emits. That is safe here **because the footprint is fixed**: both the April build and
the #574 rebuild produce the same 57 `h0` partitions (verified as a set difference in both
directions, 0 and 0), so every published file is overwritten and no stale partition can survive.

Confirm rather than assume — after a rebuild, check that no object under the hex prefix predates
the run:

```bash
curl -s "https://s3-west.nrp-nautilus.io/public-high-seas/?list-type=2&prefix=hydrothermal-vents/hex/&max-keys=1000" \
  | tr '<' '\n' | grep '^LastModified>'
```

If a future change moves points (a v3.5 upstream release, a resolution change) the partition set
can shrink, and then the prefix must be purged before repartition instead.

## Verification (the #574 acceptance checks)

Run against the duckdb-geo MCP, never locally:

```sql
-- ids agree in both directions, and identify the same feature
WITH h AS (SELECT * FROM read_parquet('s3://public-high-seas/hydrothermal-vents/hex/h0=*/data_0.parquet')),
     f AS (SELECT * FROM read_parquet('s3://public-high-seas/hydrothermal-vents.parquet'))
SELECT COUNT(*) AS joined,
       SUM(CASE WHEN h.name IS NOT DISTINCT FROM f.name THEN 1 ELSE 0 END) AS name_agrees,
       SUM(CASE WHEN h.h10 = h3_latlng_to_cell(ST_Y(f.geom), ST_X(f.geom), 10) THEN 1 ELSE 0 END) AS h10_ok,
       SUM(CASE WHEN h.h8  = h3_cell_to_parent(h.h10, 8) THEN 1 ELSE 0 END) AS h8_ok
FROM h JOIN f ON h._cng_fid = f._cng_fid;   -- expect 721 across every column
```

plus the gate:

```bash
scripts/verify-stac.py --bucket public-high-seas --dataset hydrothermal-vents   # must exit 0
```

## PMTiles

Built 2026-04-12 and **not** rebuilt by #574. Its tippecanoe footer advertises 12 attribute
fields and **no `_cng_fid`**, so the tiles carry no feature id that could be stale against the
flat — the staleness that hit the hex does not apply. The PMTiles asset's `table:columns`
(12 columns, no `_cng_fid`) matches the footer and is accurate.

Note this is the exception to the catalog-wide rule in `stac-authoring` that the tile field set
is `GeoParquet attrs − geometry + _cng_fid`: this build predates that behaviour. If the tiles are
ever regenerated, `_cng_fid` will appear and the asset schema must be re-mirrored with
`scripts/mirror-pmtiles-columns.py`.
